# Locale and translations

The components ship with English labels and automatically apply the correct
language based on where the user is. No configuration is required for the
common case — locale is detected, persisted, and updated transparently.

## How locale is determined

When the component bundle loads, it picks a locale in this order:

1. **Stored locale** — if the user has previously signed in, their locale is in
   `localStorage` from that session. This is the most common case after first
   sign-in.
2. **Your page's own language** — the `lang` attribute on `<html>`. `en-US`
   matches `en`; `zh-TW` matches `zh_TW`.
3. **Browser language** — `navigator.languages`, checked the same way, but only
   for a page that declares no `lang` of its own.
4. **Fallback** — `en` if nothing else matches.

Your page outranks the browser deliberately. The components sit inside your markup,
and a portal written in English should stay English for a visitor browsing in
German — translated buttons in an untranslated page read as a bug. **So declare
`lang` on every page.** A page that leaves it off is asking to be matched to
whatever the visitor's browser prefers.

What a signed-in user chose for themselves still wins over both: that is their own
setting, not a guess.

`document.documentElement.lang` is set to the resolved locale only where your page
left it empty — we will not overwrite a language you declared, since that attribute
describes your prose and not just our labels. If you swap your own page's language
at runtime, set the attribute yourself alongside `setLocale`.

## Locale from the user profile

Every sign-in response includes the user's saved locale:

```json
POST /api/v1/sign_in
→ { "token": "…", "expires_at": "…", "user": { "locale": "de", … } }
```

`<sa-sign-in>` reads this and calls `setLocale` automatically, so after the user
signs in their locale is applied immediately and stored for future visits. It works
in both directions and needs no code on your side: the account is where the
preference lives, and the picker on `<sa-user>` writes back to it, so a customer
who only ever visits your portal can still set a language that follows them.

## Forcing a locale

Call `setLocale` before or after mounting the components. Import it from the same
CDN URL as the bundle:

```js
import { setLocale, addMessages } from 'https://cdn.solar-assistant.io/js/solar-assistant.js'

setLocale('de')  // German — must be in the supported list, or registered via addMessages
```

This persists the choice to `localStorage` — the browser only; see
[the built-in picker](#the-built-in-picker) for saving it to the account. If the
locale code is not in the supported list it falls back to `en` and says so on the
console, so a code you expected to work does not fail quietly.

A common pattern is to call `setLocale` from a language switcher on your page
before the components connect to the DOM, so the first render already uses the
right strings. Calling it after mount has no visible effect until the next
navigation within a component — reload the page if you are switching language
while components are on screen.

## The built-in picker

`<sa-user>` already carries one, on the account page, so a portal gets a language
picker without building anything. It lists every registered locale — including any
you added with `addMessages` — each named in its own language, and on change it
sets the locale, saves it to the user's SolarAssistant account, and reloads the
page.

It saves to the account rather than only to the browser because that is the field
every other part of SolarAssistant reads: choose German on the portal and it
follows you to your next browser and beyond the portal. It reloads because the
components read their locale once at load, and because the page around them is
yours — quite possibly served per language — so a reload is the one thing that
brings both into the new language together.

If you would rather place the picker yourself, three exports give you the same
pieces:

```js
import { locales, localeName, currentLocale, setLocale }
  from 'https://cdn.solar-assistant.io/js/solar-assistant.js'

locales()            // ['en', 'de', 'fr', …] — every registered locale
localeName('de')     // 'Deutsch' — the language named in itself
currentLocale()      // 'de' — what is in force now
```

`localeName` uses the browser's own `Intl.DisplayNames`, so a locale you invented
and registered with `addMessages` is named correctly too, with no table for you to
maintain.

To save the choice to the account as well, write it to the user — `setLocale` only
ever touches the browser:

```js
await api.patch('/user', { locale: 'de' })
```

## Supported locales

| Code | Language |
|---|---|
| `af` | Afrikaans |
| `bg` | Bulgarian |
| `cs` | Czech |
| `da` | Danish |
| `de` | German |
| `el` | Greek |
| `en` | English *(default)* |
| `es` | Spanish |
| `fr` | French |
| `hu` | Hungarian |
| `it` | Italian |
| `lt` | Lithuanian |
| `nl` | Dutch |
| `pl` | Polish |
| `pt` | Portuguese |
| `ro` | Romanian |
| `uk` | Ukrainian |
| `vi` | Vietnamese |
| `zh_CN` | Chinese (Simplified) |
| `zh_TW` | Chinese (Traditional) |

Every locale carries the full set of strings; should one fall behind a new label,
that label appears in English rather than as a blank.

All but `bg` are the languages SolarAssistant offers in account settings, which is
what lets `user.locale` select them on its own. Bulgarian is contributed and ahead of
that list, so reach it with `setLocale('bg')` or a page that declares `lang="bg"`
until account settings catches up.

## Using `t()` in custom outlets

If you write a custom outlet component (see [Customizing](customizing.md)) and
want its labels to follow the same locale as the built-in components, import `t`
from the bundle:

```js
const SA = 'https://cdn.solar-assistant.io/js/solar-assistant.js'
const { t, setLocale } = await import(SA)

class AcmeSiteDetail extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: 'open' })
    this.shadowRoot.innerHTML = `
      <button id="back">${t('sites')}</button>
      <h1 id="title"></h1>
    `
    // …
  }
}
```

`t(key)` returns the string for the current locale, falling back to English if the
key is missing in that locale. The built-in keys cover common UI terms:

| Key | English value |
|---|---|
| `email` | Email |
| `first_name` | First name |
| `last_name` | Last name |
| `name` | Name |
| `description` | Description |
| `owner` | Owner |
| `role` | Role |
| `sites` | Sites |
| `sign_in` | Sign in |
| `sign_out` | Sign out |
| `save` | Save |
| `invite` | Invite |
| `view` | View |
| `connection_error` | Connection error. Please try again. |

For strings specific to your component, manage them yourself — `t()` is not a
general-purpose translation framework, just shared infrastructure for the built-in
labels.

`t` also accepts a second argument for variable substitution:

```js
t('account_created', { email: '<strong>user@example.com</strong>' })
// → "Account created for <strong>user@example.com</strong>."
```

## Adding or overriding strings

### From your own page (integrators)

Use `addMessages` to add a new locale or override specific strings in an existing
one. Import it from the bundle alongside `setLocale`:

```js
import { addMessages, setLocale } from 'https://cdn.solar-assistant.io/js/solar-assistant.js'

// Add a new locale (partial — any missing key falls back to English):
addMessages('sw', {
  sign_in: 'Ingia',
  email: 'Barua pepe',
  sites: 'Tovuti',
})
setLocale('sw')

// Or override a few English strings to fit your business terminology:
addMessages('en', {
  register_site: 'Claim your device',
  invite_user: 'Add a team member',
})
```

Call `addMessages` before the components mount so the first render already uses
your strings. `addMessages` merges into the existing dictionary for that locale —
you only need to supply the keys you want to change, and your value wins over the
built-in one. So a language we already ship can be bent to your terminology a few
keys at a time, without taking over the rest of it.

### Contributing to the built-in translations

Each language is one file under `packages/components/src/locales/`, keyed the same
as the `en` block in `i18n.js`. To add one, copy an existing file, translate the
values, and register it in the `MESSAGES` map at the top of `i18n.js`. Corrections
to a language already there are just as welcome — edit its file. Partial
translations are fine: any missing key falls back to English automatically.

Send it as a pull request against
[`Solar-Assistant/js_solar_assistant`](https://github.com/Solar-Assistant/js_solar_assistant).
If you have already translated the components for your own portal with
`addMessages`, that dictionary is most of the file.

```js
// packages/components/src/locales/de.js
export default {
  sign_in: 'Anmelden',
  email: 'E-Mail',
  // …
}
```

The locale code must match what SolarAssistant stores in `user.locale`, which
follows the BCP 47 convention except for `zh_CN` and `zh_TW` (underscore, not
hyphen).
